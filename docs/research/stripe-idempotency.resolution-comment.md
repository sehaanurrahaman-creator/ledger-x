**Resolved** — reading pass done; findings are in [`docs/research/stripe-idempotency.md`](https://github.com/sehaanurrahaman-creator/ledger-x/blob/arena/01a0920a-ledger-x/docs/research/stripe-idempotency.md) (commit `c49f269`), every claim linked to a primary source and tiered P1 (Stripe docs / Stripe engineering blogs / Stripe client-library source) vs P2 (Stripe engineer writing personally) vs P3 (observed wire payloads), with nine explicit gaps where Stripe documents nothing.

**Scope & lifetime.** Keys are account-scoped, not endpoint-scoped, ≤255 chars, sent as `Idempotency-Key` on any `POST`. Retention is a **floor** — *"remove keys … after they're at least 24 hours old"* — and at the boundary the key is **forgotten, not refused**: *"We generate a new request if a key is reused after the original is pruned."* A late retry after GC is therefore a fresh, second execution. API-version and connected-account scoping: undocumented.

**Same key, different body → 400, not 409.** The type is `idempotency_error` (*"re-used on a request that does not match the first request's API endpoint and parameters"*); Stripe's own `stripe-ruby` maps `400, 404` + `idempotency_error` → `IdempotencyError`. Stripe **reserves 409** for the concurrent case (`idempotency_key_in_use`, *"currently being used in another request"*), and its client **retries** 409. **This is the load-bearing diff: the charter's 409-on-body-mismatch contradicts Stripe's own 400/409 split**, so the 409 call needs an argument, and `STRIPE-DIFFS.md` must record it.

**Replay.** Stripe stores *"the resulting status code and body of the first request … regardless of whether it succeeds or fails"*, including `500`s, and marks replays with the header **`Idempotent-Replayed: true`** — nothing in the body. `stripe-ruby` comments that `stripe-should-retry` is expected false on 500s *"since our idempotency framework would typically replay it anyway"*. Bodies-vs-digests, and whether a replay reuses the original `Request-Id`: undocumented.

**Concurrency.** The key has an explicit in-flight state: *"If … the request conflicts with another request that's executing concurrently, we don't save the idempotent result … You can retry these requests."* → 409 `idempotency_key_in_use`. Separately, Stripe serializes per *object* via `lock_timeout` (429) and tells clients to serialize. Five key states total: absent / in-flight / complete / complete-with-different-params / **pruned**. The atomic-claim mechanism (unique index + duplicate-key error) is documented only by the engineer who built it (P2).

**Boundary.** The layer sits *behind* auth, rate limiting and validation: a `429`/`401`/parameter `400` *"can produce a different result with the same idempotency key"*. Faults must be injected in front of the layer too.

**Payouts safety.** No Stripe postmortem of a double-charge exists publicly (searched; only third-party commentary). What is documented: `pending → in_transit → paid | failed | canceled`, resolution within 5 business days, and the sharp edge — *"Some payouts that fail might initially show as `paid`, then change to `failed`."* Failures/reversals are additional records (`failure_balance_transaction`, `original_payout`, `reversed_by`), never edits. Guardrails documented as codes: `payouts_limit_exceeded`, `payouts_not_allowed`, `insufficient_funds`, `anomalous_money_movement_request` (anomaly detection blocking money movement). A published vulnerability (`wevm/mppx` GHSA-8mhj-rffc-rcvw) shows an integration that ignored `Idempotent-Replayed` accepting a replayed success as a new payment.
