**Resolved.** The decision is [`docs/adr/0004-checkpoint-replay.md`](https://github.com/sehaanurrahaman-creator/ledger-x/blob/main/docs/adr/0004-checkpoint-replay.md); the implementation is `dev.ledgerx.checkpoint` (`StateHash`, `Checkpoint`) wired through `dev.ledgerx.wal`, `dev.ledgerx.domain` and `dev.ledgerx.journal`, and the evidence is `./build.sh`'s thirteen-check checkpoint contract and `./build.sh replay`'s crash-at-every-byte campaign — 24,031 crash points across 12 seeded histories, zero mismatches, with the kill-9 harness unchanged at 1,000/1,000.

**"Byte-identical" is a function now, not an adjective.** The charter's sharpest testable property was unprovable until "byte-identical" had a definition, and the definition is `StateHash`: SHA-256 over a canonical serialization of the materialized state — accounts in opening order, each with its balance, pinned by the journal length. Fixed-width fields and lengths, big-endian, no delimiters and no escaping, resting on the ADR 0002 fact that an account id's alphabet excludes every byte a length prefix makes unnecessary to quote. **The event count is in the hash** because balances alone do not pin a history: post 5 and counter-post 5 and every balance is unchanged, and a hash that called that state identical to never-having-posted would make a lost transaction invisible — the contract asserts exactly that near-miss.

**The determinism rules are bans with reasons.** No wall-clock time (two folds of one log must agree; the contract asserts a checkpoint of one state is byte-identical however it was produced). No random (ids are caller-chosen references; the ledger mints nothing). No map-iteration order (the encoding walks opening order, a pure function of the event sequence; swapping the order changes the hash, which is the assertion that order is *signal*). And **no LSNs** — the subtle one, argued via the marker: a crash inserts a `RECOVERY_MARKER` and shifts every later LSN by one while the ledger state stays the same, so an LSN in the hash would make *crash, recover, continue* land on a different final hash than a clean run. The journal *length* is state; the log's internal position *units* are not. When the idempotency table arrives it appends its own section in canonical key order and the version byte moves — a hash change is a format change, the same trade ADR 0003 made with the type table.

**The checkpoint is one file** — 36-byte header (`u32 magic "LCHK"`, version, flags, header size, reserved, `u64 watermarkLsn`, `u64 watermarkOffset`, `u32 stateLength`, header CRC), the canonical state bytes, a SHA-256 of exactly those bytes, and a CRC32C over the whole file. Three integrity layers with three jobs: the hash is the *identity* (the same function the replay proof compares, so a checkpoint's state and a replayed state are comparable by construction — the file carries its own witness), the whole-file CRC is the *damage* detector, the header CRC is an early foreign-file rejection. The state section being exactly the hash's preimage is deliberate: two encodings of one state is the same disease as a second copy of the LSN.

**The swap is force-log → write-temp → fsync → atomic rename → fsync-dir**, each step the one that survives a crash at it. The log force is routed through the committer as a queue barrier (`Wal.force()`), so the watermark it returns is the committer's own number and the ordering ADR 0003 §10 handed this ticket holds mechanically: *the bytes a watermark names are durable before the snapshot claiming them exists, never the reverse.* The state is serialized under the ledger's commit lock, so the watermark and the bytes are the same moment. If the filesystem will not promise atomic rename, the swap refuses rather than degrade. **Retention is one line because the log is not truncated:** one live checkpoint per directory, superseded in place; the temp is the only garbage there ever is; replay-from-scratch never depends on the checkpoint, so deleting every checkpoint file is always safe — which is the strongest retention property a checkpoint can have. Truncating behind the checkpoint would make it load-bearing and need numbered segments and a manifest to be crash-safe; that is the rotation ticket's substance, declined here on purpose.

**Recovery validates before it repairs — the order is this ticket's own finding.** With a checkpoint present, `DurableLedger.open` scans the log read-only, cross-checks the checkpoint against that scan (the watermark offset within the surviving bytes; the frame its LSN names ending at *exactly* the claimed offset — dense LSNs turn "does this checkpoint describe this log?" into a frame-end comparison), and only then opens for repair. The first draft had the order backwards, and the contract's "the refusal edited the log" assertion failed: a refusal for data loss had already cut the tear and appended a marker. The two verdicts split on one question — *is the disagreement between two durable artifacts, or is one artifact internally broken?* A checkpoint that fails **its own** checks (bad magic, bad CRC, bad digest, truncated, impossible) is renamed to `checkpoint.rejected` — evidence kept, never deleted — and recovery proceeds from scratch, because the checkpoint is an optimization and the from-scratch path is proven to reconstruct the identical state; a damaged optimization must not become an outage. A checkpoint that is **intact but disagrees with the log** is `CHECKPOINT_MISMATCH` and refuses to open, because the covered bytes were forced before the checkpoint existed — their absence is lost acknowledgements, not a torn tail, and silently replaying from scratch would paper over exactly the data loss the charter exists to surface. Deleting the checkpoint remains the operator's way to choose from-scratch replay: a decision, named in the exception message, not a surprise.

**The domain's restore surface is one static factory.** `InMemoryLedger.restored(accounts, balances, eventCount)` builds a ledger whose journal begins at the watermark: restored balances, tail-only in-memory events, `size()` continuous across the restore, `audit()` folding the tail on top of the restored base and counting restored accounts as log-opened, posting validating against restored balances as ordinary balances. Every field stays final and the restore state is fixed in a private constructor — the first draft used three non-final fields and the domain's no-mutation-surface property rejected it by reflection, which is a check earning its keep by being annoying at exactly the right moment. That the checkpoint is *actually used* is asserted, not assumed: 12 steps, checkpoint at 6, and the reopened ledger holds 6 in-memory events and journal position 12.

**The proof: a crash at every byte, not only at every LSN boundary.** Crashes do not land on record boundaries — they land mid-frame, mid-payload, mid-LSN — so the harness sweeps every byte offset of every history, reconstructing the exact disk state at each: the log truncated to *o*, plus the checkpoint that was live then (checkpoints are byte-identical files, so re-planting recorded bytes *is* replaying history). Four verdicts per offset, all required: **checkpoint + tail** equals the clean prefix's exact canonical bytes; **full replay from scratch** equals it too; **crash-recover-continue** — posting the rest of the history through the recovered ledger and reopening — lands on the clean run's *final* bytes (the verdict that fails if an LSN leaked into the hash or the marker left a trace in state); and **torn heads refuse** with the log untouched. The CI-sized run: 12 seeded histories × 40 accepted steps across the fsync menu, a checkpoint every 7 steps, **24,031 crash offsets, 23,347 tears cut, 1,514 continue-checks, zero mismatches**, 49 s. The extended campaign (40 × 60) is also zero. The kill-9 harness stays and stays green — 1,000/1,000 cycles, zero acked-but-lost forced transactions — because real process death and the byte sweep are complements: one is end-to-end, the other is exhaustive, and neither claims the fault surface the other covers (a lying controller is out of scope by ADR 0001; the ADR states the gap in each harness).

**Stated plainly, what this does not decide:** auto-checkpoint policy (the trigger needs the benchmark's latency numbers before a default can be honest — `writeCheckpoint()` is explicit until then); log truncation behind a checkpoint (see above); and the idempotency table itself, whose section in the canonical state is now a rule its own ticket inherits.

**Handed to other tickets, as rules rather than notes:** the idempotency table joins the hash as a versioned section in canonical key order; rotation turns the watermark into (segment, LSN, offset) with a per-segment frame-end check and keep-newest-K retention; the chaos fault set's storage half is fully named — log head (refuse), log tail (cut), checkpoint file (discard), swap (atomic or not at all) — each with its required verdict; TLC gets two one-line properties (fold determinism; coverage: checkpoint ⊑ log ⇒ recovered = fold(log)); and the benchmark gets a checkpoint column — state-size bytes, three forces, recovery with and without.

**Fog graduated:** the map's *Not yet specified* loses the **replay state-hash scheme** — decided, in code, checked at every byte offset of every CI run.
