**Resolved.** The decision is [`docs/adr/0004-checkpoint-replay.md`](https://github.com/sehaanurrahaman-creator/ledger-x/blob/main/docs/adr/0004-checkpoint-replay.md); the code is `src/main/java/dev/ledgerx/checkpoint/` (six classes) wired into `DurableLedger` and `InMemoryLedger`; the evidence is `src/test/java/dev/ledgerx/checkpoint/CheckpointContract.java` — 13 checks, run by `./build.sh` on every build.

**"Byte-identical" needed a definition before it could be a test, so that is the decision.** State is a **canonical serialization** — one row per account, `(id, kind, balance)`, sorted **by account id**, fixed-width, length-prefixed, no delimiters — and the state hash is **SHA-256 over exactly those bytes**. A ledger holding `alpha ASSET −12345, beta LIABILITY +12345` serializes to 37 bytes and hashes to `0a4815c507a759141b878e5e9640e7d4a340b37e1199e07d3bc2ad0ecbc4ff19`; both are pinned in the contract suite, and the digest was cross-checked against `hashlib.sha256` outside this codebase so the pin is a fact about the encoding rather than a transcript of what the code printed.

**The determinism rules, i.e. what is banned from state and why each ban is load-bearing.** No wall-clock timestamps (inherited from ADR 0002; it also answers standing design-review question 5 for state — *there is nothing for two clocks to disagree about*). **No map-iteration order — and this one is subtler than it looks:** the obvious order, account-opening order, is *not* a function of the state, because a ledger restored from a checkpoint opens the checkpointed accounts first and the tail's accounts after, while a from-scratch fold opens them in log order; two paths through the same history would serialize the same money differently and hash differently, so the rows are sorted by id. No random or generated ids. No floating point. And the ban this ticket adds: **nothing positional** — no LSN, no offset, no record count — because ADR 0003 §2 makes LSNs unique only within a surviving prefix, so a hash that mentioned position would change when the money did not. The corollary is the definition worth keeping: *state is what is left when you forget how you got there.*

**The checkpoint format** is 68 bytes of header around those exact bytes — `u32 magic "LCKP"`, version, flags, header size, `u64 lastLsn`, `u64 walBytes`, `u64 journalEvents`, `u32 payloadLength`, `u8[32] stateHash` — then the payload, then a CRC32C over the whole file. **The payload *is* the hash preimage**, so one encoder serves both the live hash and the file, and "the file says X and the code computed Y" cannot be a disagreement between two encodings. Two integrity layers, because they answer different questions: the CRC catches a torn file, and SHA-256 catches a writer that stored the *wrong state* — which no CRC can see, because a CRC over the wrong bytes is a perfectly good CRC. No timestamp, no host name, no process id: nothing true of the writer rather than of the state.

**The atomic swap** is serialize whole → write `checkpoint.<lsn>.tmp` in the *same directory* (a cross-device rename is a copy, which has exactly the half-written window this prevents) → `fsync` the file (metadata, because the rename is about to publish its name and size) → `rename` with `ATOMIC_MOVE` → `fsync` the directory. There is no instant at which the live name points at a partial file, and none at which there is no live file at all — which is why a checkpoint needs no generation counter and no manifest.

**Retention is one live checkpoint, replaced in place**, and the honest reason is that **replay-from-scratch does not depend on a checkpoint at all**: this repository never truncates the log (ADR 0003 §11 leaves rotation unstarted), so a checkpoint is a pure optimisation, GC is unlinking orphan scratch files, and deleting every checkpoint costs time and nothing else — asserted, not claimed. Keeping N was refused: it buys a faster recovery from "the newest one is corrupt" at the cost of a selection rule, a GC rule and N times the crash window, for something already correct-but-slow. **The trigger that changes the trade is written down**: the day the log is rotated, a checkpoint stops being a cache and becomes load-bearing.

**Recovery is checkpoint + tail**, and the tail is "every record with an LSN above the watermark" — where the watermark is *checked against the log* rather than believed, three ways: the file must parse and self-check; the baseline must be a possible state (Σ balances = 0 is invariant, so one that is not describes a ledger the log could not have produced); and the watermark must still be true of the log. **That third check is the one this ticket would have shipped without.** ADR 0003 §2 warns that LSNs are unique only within a surviving prefix, so: run A appends LSNs 1–10 and checkpoints at 10; a crash tears the tail at 6; recovery cuts, marks, and the writer goes on to 13. The stale checkpoint passes both the byte test (the file is longer) and the LSN test (13 ≥ 10) — and using it would fold 11–13 on top of a state still containing the *old* 7–10, resurrecting transactions recovery had already discarded. Comparing the claimed offset against the current end offset of the record it names catches it exactly, and costs one array the scan was already computing. The scenario is in the suite end to end: cut below LSN 20, regrow to 26, put the stale snapshot back — discarded as `NOT_A_RECORD_BOUNDARY`, and the recovered state equals the from-scratch fold.

**A checkpoint that fails any check is discarded and the whole log folded — and the asymmetry with ADR 0003 is deliberate, not an inconsistency.** A damaged *log* is a repair or a refusal, because the log is the only record of what was promised to a client, so damage to it is a choice between a receipt and some money. A damaged *checkpoint* is a cache miss, because every claim it makes the log can still be asked to re-derive. Folding from byte 0 is expensive and correct; guessing is cheap and might be money.

**The harness the ticket asked for, and what it actually does.** For each of 400 random histories, for **every** LSN boundary — every point a crash can land, including the empty log and the whole history — cut the log there and recover **three** ways: with whatever checkpoint is on disk, again with the checkpoint the first recovery wrote, and again after deleting the checkpoint so recovery must fold from byte 0. Each digest is compared with the digest of the same prefix folded **in memory, with no files involved at all**. At the extended campaign: **26,000 boundaries × 3 recoveries, 100% byte-identical, zero mismatches** (`LEDGER_X_CKPT_HISTORIES=400 LEDGER_X_CKPT_OPS=60 ./build.sh test`; CI's default run is 1,160). The other 12 checks enumerate what a random crash cannot be relied on to hit: **all 145 truncations** of a 144-byte checkpoint, each a cache miss and never a wrong state; **six doctored files**, each with the CRC recomputed so the check under test is the one behind it — a balance off by one minor unit and a scribbled digest field both `HASH_MISMATCH`, an LSN one short and an offset one byte short both `NOT_A_RECORD_BOUNDARY`, an offset past the end and a watermark past the end both `STALE_WAL_BYTES`; a baseline summing to 1 minor unit refused as `IMPOSSIBLE_STATE`; a scribbled segment header beside a valid checkpoint still refusing to open, file untouched, so a checkpoint cannot soften ADR 0003; and `NO_FSYNC` refusing to snapshot records the log has not made durable.

**Three findings, in the order they cost time.** (1) *The soundness guard was measured, not argued.* A checkpoint may only be written when memory and the durable log agree on how far they go; with that check disabled, a `NO_FSYNC` ledger holding 16 unforced records happily wrote `Checkpoint[lsn<=16 @byte 16, 16 events]` — claiming 16 records at byte 16, which is the *start* of record 1. A power cut then took the tail, and recovery discarded it as `STALE_LSN` and correctly recovered the empty state. So the guard is the explicit refusal at write time and the staleness checks are the backstop at read time — defence in depth, both halves now verified. (2) *An existing test broke, and it was right to.* `WalContract`'s "replay is deterministic and byte-identical" failed with `206 live, 206 and 0 replayed`, because the second open used the checkpoint the first had written and its in-memory event list held the empty tail: **after a checkpointed recovery `InMemoryLedger.events()` is the tail, not the history** — the history is the WAL, and the state hash is what replaces the event list as the thing to compare. The check was rewritten to compare what the claim is about (the log folded from byte 0 twice, *and* the checkpoint-plus-tail recovery reaching the same digest), which is strictly stronger than before. (3) *The harness's own first run was wrong in a diagnostic way:* cutting to boundary *k* then *k+1* does not work, because `FileChannel.truncate` cannot grow a file — and the symptom is why the check is shaped this way, since all three recovery paths agreed with each other while disagreeing with the in-memory fold, so a harness comparing only recoveries would have passed.

**What this does not prove, stated plainly.** No `SIGKILL` aimed at the rename on real hardware: the harness simulates the swap's outcomes (an orphan scratch file, a truncated checkpoint, a stale one) rather than racing it, which is what a checkpoint-specific chaos run would add. No `O_DIRECT`, no `mmap`, no filesystem other than this sandbox's. No measurement — the cost arithmetic is in the ADR, and the benchmark ticket owns the numbers, including the honest one: under `NO_FSYNC` the checkpoint count is zero, and that is the policy's promise rather than a bug.

**Handed to other tickets, as rules.** To *What are ledger-x's idempotency semantics?*: the idempotency table **joins the canonical state** under a new canonical version rather than getting its own hash — a key that survives a crash in the log but not in the state is exactly the double-payout the charter is about, and two digests can disagree while each is individually correct. To *How do a payout and a refund to the same account never interleave?*: `checkpoint()` takes the commit lock, because a snapshot taken while an append is in flight would claim a watermark the log has not reached; and the `appliedLsn`/`forcedLsn` pair is the "ack order equals apply order" hook that ticket needs, already present. To *What must TLC prove?*: the spec now has a **state function** rather than a state variable, and the lemma worth exhausting is that a watermark validated against the log cannot admit a stale snapshot. To *What breaks it?*: the fault set gains four entries — truncate the checkpoint at any byte, scribble its payload, forge its watermark, delete it — and the oracle is the first one in this project that fits in 64 characters.

**Fog graduated:** the replay **state-hash scheme** comes off the map's *Not yet specified*. The chaos fault set's payout half stays, now sharper: the storage half is fully named and fully walked, and what remains is *combinations* — a kill aimed at the rename, and simultaneous damage to the log and the snapshot.
