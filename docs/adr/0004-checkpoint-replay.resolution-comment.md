**Resolved.** The decision is [`docs/adr/0004-checkpoint-replay.md`](https://github.com/sehaanurrahaman-creator/ledger-x/blob/main/docs/adr/0004-checkpoint-replay.md); the implementation is `dev.ledgerx.checkpoint` plus the recovery path in `dev.ledgerx.journal`, and the evidence is `./build.sh`'s twelve-check checkpoint contract and `./build.sh boundary`'s crash-at-every-prefix harness.

**The checkpoint is a file named for its watermark.** `<ledger>/checkpoints/checkpoint-<19-digit lsn>.lckp`, a 72-byte header, the canonical state section, then a 36-byte trailer: a `u8[32]` state hash and a `u32 crc32C` over everything before it. Big-endian, and built from `WalFormat`'s primitives so the two formats of this repository cannot disagree about what a length is. Three copies of the watermark — the name, the header and the state section — are checked against each other, because a file's name is the one part of it a rename can change without touching a byte. Nineteen digits is `Long.MAX_VALUE`'s width, so name order is watermark order; recovery nevertheless sorts by *parsed* watermark, because a change to the padding must not be able to silently reorder which checkpoint is believed.

**The swap is the order ADR 0003 §10 handed over, and each step earns its place.** Delete a stale temp before opening it (otherwise a crashed swap's leftovers get appended to and the result is renamed into place two-checkpoints long under one name); write; **`forceAll`, not `forceData`** — a checkpoint's *length* is part of its claim, unlike a WAL segment's, whose length is recoverable from its tail; `rename(2)` in the same directory; **`fsync(dirfd)`**, because a rename is a directory entry; then collect. Retention runs only after the new name is durable, which is the protocol's one ordering constraint. `crc32C` catches a tear, `stateHash` catches a file that is internally consistent but not the state it claims, and `walDigest` — SHA-256 over exactly the covered log bytes — catches a checkpoint applied to another history, which is the layer that matters because ADR 0003 §2 **reuses LSNs after a cut**, so a watermark is not an identity. The contract proves that with two histories at the same LSN covering the same byte count, told apart only by the digest.

**The state hash, defined once.** SHA-256 over the canonical serialization of the materialized state: canonical version, `lastLsn`, account count, then accounts **in the log's opening order**, each with its kind as a *name* (the WAL uses an ordinal because a log is versioned with its reader; a state hash is a number a human compares between builds), its id, and its signed balance in minor units. `lastLsn` is inside the hash deliberately: the same balances at a different point in the log are not the same state, and the position is what makes "checkpoint + tail" comparable to "replay from scratch" as one equality. Each account carries its own balance, so the state is one list rather than two collections that can disagree. The event list is **not** in it — the log *is* the history, and a checkpoint that carried it would be a copy of the log — so byte-identical is a conjunction, and all of it is checked: the state hash across the run, the recovery and a fold from byte 0; the WAL contract's re-encoded-payload comparison for the entries; the `walDigest` binding the state to exact log bytes; and the boundary harness requiring the crashed log to be a byte prefix of the uninterrupted run's.

**The determinism rules are enforced rather than asserted.** No wall clock (two replays at different instants must hash the same); no randomness (`UUID`, `SecureRandom`); no map or set iteration order — the serializer reads a list in the log's opening order, and hash containers are banned from the path; no identity hash or default `toString`; no default locale or charset (all text on the path is explicitly ASCII); no floating point (ADR 0002's rule, and the lint enforces it under the domain); no JVM, host or environment identity; and no filesystem listing order. "Hashed after every commit" is a property of the *function* — `stateHash()` exists at every instant and the harness compares it at every prefix — while the *file* is written on a cadence, default every 1,024 commits, with a configuration that checkpoints every commit exercised so both halves are tested.

**Recovery, and why a refusal never costs money.** The loader lists candidates newest first, verifies each against the log — name, coverage (`coveredBytes` must be the offset the log itself says the watermark's frame ends at), and the log digest — and uses the first that stands: `state.restore()` seeds the accounts and balances, and only the tail is folded. The ten `CheckpointRefusal` values are a closed list, and every one of them means *skip this file*: if none stands, the caller folds from byte 0 and loses only time. That is the deletion theorem — a checkpoint is a cache of a fold, so deleting any checkpoint cannot lose money — and the contract asserts it by deleting every checkpoint and requiring the same hash back. Retention keeps the newest `retain`, default two (one to use, one to fall back to), and needs no atomicity of its own for the same reason: a crash that resurrects a deleted checkpoint leaves a directory with one extra valid file.

**The harness: every prefix of a seeded history, crashed, recovered, hashed.** `dev.ledgerx.checkpoint.crash.LsnBoundaryHarness` runs a history in a child JVM, kills it with `kill -9` at every prefix boundary, and requires five hashes to agree — the crashed run's own, the uninterrupted golden run's at the same prefix, the recovery's, a fold from byte 0, and a recovery with every checkpoint deleted — with two structural checks on top (the crashed log is a byte prefix of the golden run's; a boundary crash tears nothing) and a resume that replays the rest of the history into the recovered ledger and compares hash for hash to the end, so a recovery that lands on the wrong prefix diverges instead of looking plausible. Three configurations cross the fsync menu with the cadence menu: per-commit with no checkpoints, group commit with one per commit, and no-fsync with one per third commit. On top of that it kills the writer *inside the swap*, at all five stages and three arms each — before the temp is forced, after it, after the rename, after the directory sync, after collection — because a boundary crash cannot test the swap and an ordering has to be tested by killing inside it. Result on this build: **`PASS 81/81` cycles, 81 real `SIGKILL`s, zero recoveries that refused a surviving checkpoint, zero cycles where checkpoints existed and were not used.** The kill is an external `kill(1)` — the JDK refuses `destroyForcibly()` on the current process — and a child that cannot signal itself says `HALTING` and is not counted, so the harness can never be mistaken for testing a clean exit.

**The contract covers what a random kill cannot be relied on to hit** (`PASS 12/12 checkpoint checks`): the file's bytes at every field offset; every integrity layer producing its own named refusal, including a state section re-hashed and re-CRC'd so only the state's own version check can refuse it; a renamed file refused by name; a truncated log refusing a checkpoint as `COVERAGE_GONE`; two histories at one watermark told apart only by the log digest; a corrupt newest falling back to the older one with **exactly one tail record folded**; retention and stale-temp deletion; the swap's stages in declared order; the state hash's sensitivity to opening order; a restored ledger that audits and keeps going; and the ticket's central equality at one watermark, three ways.

**What it costs, including the unfavourable row.** A checkpoint write is O(covered bytes) for the binding digest plus O(state) to write and force it: measured 73 ms for 22,000 records with a 47 KB state, 93 ms for a 489 KB state. A checkpointed reopen is *not* automatically faster — it must still scan the log and re-derive the digest — and the honest numbers say so: 114 ms against 169 ms folding 22,000 records, but 134 ms against 128 ms when the state is large and the log short. The checkpoint's reasons to exist here are the *proof* and a *bound* on the tail a recovery folds, not raw speed at these sizes; §7 of the ADR states the trade with both rows rather than one.

**What this clears and what it hands on.** The map's *Not yet specified* item "The replay state-hash scheme — how byte-identical is canonicalized" is answered by §3 and §4. To *What are ledger-x's idempotency semantics?*: the key table joins the canonical state under §4 — fixed order, and **no wall-clock value inside the hash**, because an expiry stored as an absolute instant would move the hash without a commit. To rotation (still unstarted): the precondition now exists, and the order remains snapshot → directory sync → truncate, never the reverse. To *What must TLC prove?*: the replay predicate is now a function, `stateHash(replay(log[0..n])) == the hash the run recorded at n`, plus "a used checkpoint's `walDigest` equals the digest of the log prefix it was taken over". To *What breaks it?*: the checkpoint fault set has defined outcomes — tear it, flip it, rename it, truncate the log under it, copy it between directories — all ten refusals named. To *How fast is it, honestly?*: §7's arithmetic.
