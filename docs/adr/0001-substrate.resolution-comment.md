**Resolved** — the ADR is [`docs/adr/0001-substrate.md`](https://github.com/sehaanurrahaman-creator/ledger-x/blob/main/docs/adr/0001-substrate.md) (merged in [#19](https://github.com/sehaanurrahaman-creator/ledger-x/pull/19)), and the CI skeleton on the chosen stack is green on `main`.

**The call: Java 21 (LTS) with virtual threads, on a hand-rolled append-only WAL owned by this repository.** No storage engine dependency. RocksDB rejected; Go rejected — both with the reasoning written down, including the places where they were stronger.

**Fsync control was a tie, not the decider.** Java reaches both syscalls through one boolean: `FileChannel.force(false)` is `fdatasync(fd)` and `force(true)` is `fsync(fd)` — literally the branch in `Java_sun_nio_ch_UnixFileDispatcherImpl_force0` on jdk21u. But Go reaches both too: `os.File.Sync()` is `syscall.Fsync`, and `syscall.Fdatasync` exists in the stdlib on Linux, just outside the `os.File` abstraction on a raw fd. Capability is even; Java wins on API shape only. The ADR says so rather than overselling the criterion.

**RocksDB is rejected on ownership, not on fsync.** It does expose the choice — `use_fsync` defaults to `fdatasync`, and `WriteOptions.sync==true` is documented as "a `write()` system call followed by `fdatasync()`". What it does not give us is the *timing*: `manual_wal_flush` means either RocksDB cuts its own WAL groups (we no longer own the group boundary) or we flush manually and forfeit the batching the metrics table exists to measure. Either way the third question on this ticket — what group commit looks like — gets answered by RocksDB's internals, and the record format and torn-tail rules that *What does a durable write look like?* exists to decide get inherited instead of designed. The counterweight is recorded in the ADR, not buried: RocksDB would have handed us the memtable, SSTables, compaction, block cache and crash-consistent recovery — roughly one subsystem not written.

**Go is rejected on the TLA⁺ leg.** TLC is itself a Java program ("It is also coded in Java" — Lamport), and the TLA⁺ tools need a JVM. On Go the spec and the implementation live in two languages, two toolchains and two CI jobs, with the seam exactly where the proof is supposed to touch the code. Goroutines having no pinning trap is the one place Go is genuinely better, and the ADR says so.

**"Commit" on this stack:** the record's bytes are in the WAL and the group's `force(false)` (`fdatasync`) has returned. A single committer thread batches appends from many virtual threads and issues one `fdatasync` per group; callers park on the group, never a thread per write. `force(true)` (`fsync`) is for open, close, rotation and checkpoint, plus an explicit `fsync` of the WAL's **directory** at create/rotate/checkpoint-swap. `force(false)` per group because the log is append-only and its length is recoverable by scanning the tail — that is the first real answer to standing design-review question 1 (write amplification).

**One hard rule the substrate forces:** per-account ordering uses `ReentrantLock`, never `synchronized` — a virtual thread that blocks in a `synchronized` block is *pinned* to its carrier on Java 21. The machinery is in `VirtualThread.java` (`PINNED`/`TIMED_PINNED`, `VirtualThreadPinnedEvent`) and the JDK ships `-Djdk.tracePinnedThreads`, but `Thread.java` — the file everyone reads — never contains the word "pin". It is still in `VirtualThread.java` on `openjdk/jdk` master, so the rule is permanent; it is enforced mechanically by `scripts/lint.sh` (a `synchronized` in `src/` fails the build) and it is load-bearing input to *How do a payout and a refund to the same account never interleave?*.

**An honest gap: Jaunt.** The charter says TLA⁺ runs via Jaunt inside the JVM. Searched 2026-09-11 — GitHub repository search for `jaunt` and `jaunt tla` in name/description returns no TLA⁺ tool (the only Java project by that name is a web-scraping library), and a web search finds no Jaunt/TLA⁺ toolchain either. The ADR therefore records a **requirement** ("TLC runs from a clean checkout, in CI, in one language") rather than assuming a tool, with TLC's own `tla2tools.jar` as the fallback, and the assumption is graduated as its own blocking ticket rather than left to ride into the spec work.

**Green CI skeleton, verified.** `./build.sh` is the one command: style lint → `javac --release 21 -Xlint:all -Werror` → the substrate contract test. Zero third-party dependencies, so nothing resolves from a registry. On `main`, merge commit `eda1ea5` (run `34838742618`) publishes its verdict as run annotations — `notice: PASS 5/5 substrate checks` and `notice: substrate contract measured platformThreads=10 platform threads`; the branch that carried the decision ran the same job eight times, every one `completed/success`. The five checks pin the platform facts the ADR rests on: Java ≥ 21; **10,000 concurrently-parked virtual threads running on 10 platform threads** (measured, not asserted — the check's ceiling is 1,000); `force(false)` **and** `force(true)` both reachable with the bytes readable back; `fsync(dirfd)` available; and a per-account `ReentrantLock` serializing 64 contending virtual-thread writers with max-concurrency 1. The only code shipped is `DurableChannel` — the four durability primitives, no accounts, no entries, no balances: decision recorded, not implemented.

- [How does TLC actually run here — Jaunt, or TLC's own tla2tools.jar?](https://github.com/sehaanurrahaman-creator/ledger-x/issues/18) — the Jaunt gap above, blocking *What must TLC prove?*.

Nothing was struck from *Not yet specified*: the chaos fault set and the benchmark workload are both only *half* unblocked by this decision (each still hangs on the payout protocol and the domain model respectively), and the CI-budget fog still waits on timing data.
