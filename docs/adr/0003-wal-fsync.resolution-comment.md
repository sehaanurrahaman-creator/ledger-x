**Resolved.** The decision is [`docs/adr/0003-wal-fsync.md`](https://github.com/sehaanurrahaman-creator/ledger-x/blob/main/docs/adr/0003-wal-fsync.md); the implementation is `dev.ledgerx.wal` plus `dev.ledgerx.journal`, the evidence is `./build.sh`'s nineteen-check durable-write contract and `./build.sh crash`'s 1,000 `SIGKILL` cycles.

**The record format.** A file starts with a 16-byte segment header — `u32 magic "LWAL"`, `u8 format version`, `u8 flags`, `u16 header size`, `u32 reserved`, `u32 crc32C` over the first 12 — and then frames, append-only, never rewritten:

```
u32 frameLength  u64 lsn  u8 type  u8 reserved  u16 payloadLength  payload  u32 crc32C
```

**20 bytes of framing per record**, big-endian, and the CRC covers the length, the LSN, the type *and* the payload — not the payload alone. That is what makes a torn tail detectable rather than half-parsed: a scribbled length would otherwise order recovery to skip 4 GiB, and a scribbled LSN would read as a deliberate gap. The length covers the whole frame including itself and the CRC, so a scan walks offsets without parsing anything, and `payloadLength + 20 != frameLength` is a checkable inconsistency rather than a detail. The LSN is **dense from 1** — frame *n* carries *n* — because a mere increasing counter cannot tell a record lost after an ack from a record that was skipped on purpose; under the dense rule both become a tear at a known offset, which is the only failure mode recovery knows how to handle. It is not derived from the byte offset, because an offset cannot distinguish "the event at 4,120 is missing" from "that frame is a recovery marker and has no event". It is assigned by the log and never supplied by a caller: a caller that can name a number can name a stale one.

**The type table is closed** — `ACCOUNT_OPENED`, `POSTED`, `RECOVERY_MARKER`, and 0 which is *not* a type because 0 is what damage reads as — so an unmapped byte is a fatal finding rather than a record to skip, which makes adding a type a version bump: an old reader refuses a new log, and a refusal can be survived by upgrading. Payload is the two ADR 0002 event kinds with lengths and fixed-width fields and no escaping (`u8 kind | u8 idLen | id` and `u16 entryCount | (u8 idLen | id | u8 side | i64 minorUnits)*`); the 64 KiB payload ceiling is the entry-count ceiling ADR 0002 handed to this ticket, and it comes out at **5,957 entries** at one-byte ids, bounded by the frame rather than by the `u16` count. CRC32C because `java.util.zip.CRC32C` is `@since 9`, its bulk `updateBytes` is an `@IntrinsicCandidate`, and its Java fallback is slicing-by-8 over 8×256 tables rather than a bit loop — so the worst case is a table walk and the best case is an instruction; `@RFC 3720`, polynomial `0x1EDC6F41`. No transaction id, no timestamp, no currency code and no idempotency key inside a payload, each with the reason written down in `EventCodec`'s javadoc; question 5 (clock skew) answers itself for the storage layer, because the log reads no clock, so replay is deterministic by construction.

**The fsync menu**, selectable per commit because `FsyncPolicy` is a value carried by the append rather than a process-wide mode: `PER_COMMIT` (ack after this record's `forceData`), `GROUP_COMMIT(maxRecords, maxDelay)` (ack after the group's — the default, 64 records or 2 ms), and `NO_FSYNC` (ack after `write()` returned). A group is one `write()` and at most one `fdatasync`; members that waived the promise are acked before the force, so a caller that waived it is never made to wait for somebody else's. **The ack rule** is the thing the rest of the map leans on, and it is implemented in exactly one place: a future completes after the force whose range contains its bytes returned — `PER_COMMIT`'s own, `GROUP_COMMIT`'s group — and under `NO_FSYNC` "durable" means only "this process can no longer lose it".

**Where fsync goes and why:** `force(true)` + `fsync(dirfd)` at create (a created file whose directory entry is not durable can vanish; `fsync(2)` says "calling fsync() does not necessarily ensure that the entry in the directory containing the file has also reached disk. For that an explicit fsync() on a file descriptor for the directory is also needed"); `force(true)` at open, which is what makes the recovered prefix durable before the first new byte, including tail bytes a no-fsync predecessor left in the page cache; `force(false)` per forced group, because the promise a commit needs is data and the file's length is recoverable from the tail; `force(true)` after a torn-tail truncation — **stated against ourselves**, the same man page says a size change from `ftruncate(2)` "would require a metadata flush" even for `fdatasync`, so `force(false)` would do on Linux; `force(true)` at close, because a clean exit is not a crash and bytes the log holds are flushed rather than abandoned.

**The torn-tail rules**, sharpened from "stop at the first CRC failure and truncate" into three parts. *Classify before repairing:* a finding that a partial write could have produced — short frame header, dishonest or over-long length, frame past EOF, CRC mismatch, LSN hole — is **cuttable**, and a finding that requires a complete, CRC-matching frame — unknown type, payload that will not decode, a posting the ledger refuses, head damage — **refuses to open**, file untouched. The asymmetry is the whole rule: damage from a crash can live only at the tail, so only the tail may be repaired; everything else is data, and truncating at it would delete acked money to work around damage that cannot have come from a torn write. *Cut, never skip:* leaving a hole would put the next appends behind it, where the next scan stops at the hole and never reaches them — acked, durable, and invisible forever; cutting is also what keeps recovery idempotent, which the harness asserts after every cycle. *Why it is safe* is the lemma the ticket asked to be argued: no record past the last durable `force` was ever acknowledged, and recovery cuts at the first invalid frame, which is at or past the last valid one, so the discarded set is disjoint from the set ever acknowledged — which is the exact sense in which recovery can never be choosing between a client's receipt and a client's money. The one loophole is a policy's and not the format's: an acked-but-unforced record under `NO_FSYNC` sits past the watermark and gets cut, and that is what that policy promises.

**Recovery appends one `RECOVERY_MARKER`** after a cut — reason, bytes cut, records kept, last surviving LSN — forced whatever the policy says, because it is a statement about the log rather than a transaction. It is *not* a resurrection guard, and the ADR says so rather than taking credit: dense LSNs plus truncation already prevent that. What it buys is that the file is self-describing about its own repair, which is the difference between "the writer died at this byte" and "recovery cut here, and here is why" when somebody asks how a transaction went missing. It reports the bytes **recovery cut**, not the bytes the crash lost: a log cannot report data it never saw.

**Write amplification** (question 1), as arithmetic the metrics ticket replaces with numbers rather than as a number: 20 fixed bytes per record, of which 8 are the LSN; a two-account transfer with realistic 16-character ids is a 52-byte payload in a **72-byte frame**; 12 entries is 266 into 286; the recovery marker is 41 bytes at most once per open; a group of *k* records is one `write` and one `fdatasync`. Measured on this build: 51 records of 4-byte payloads under no-fsync produced a 1,240-byte file — **exactly 24 bytes per record** — and 24 one-byte-payload records under per-commit produced 504 bytes of frames. Syscalls are what actually separates the menu (1+1 per transaction; 5 forces for 256 records at 32-way load; 0 forces for no-fsync), and because a flush moves whole pages, an `fdatasync` after a 72-byte append costs the device up to a 4 KiB block — ~57× at the block layer for a lone small commit against ~1.8× for a 64-record group: **that is where group commit's real win lives, the page and not the syscall.** Ext4's journal and `data=ordered` add writes on top and this sandbox cannot see below the filesystem, so the paragraph is labelled as arithmetic. Not spent: full-page images (there are no pages to tear in an append-only log of logical records), compression (a write-path compressor would have to be deterministic across JDK versions to keep replay byte-identical), a per-record back-pointer (Postgres carries `xl_prev` to walk backwards; recovery here reads forward), a second checksum layer (a payload-internal digest is a field a corrupt writer could leave consistent).

**Two findings the harness earned, both in the ADR rather than tidied away.** The first 1,000-cycle campaign's `group:64:5000` cycles took 90 seconds against 0.3 s for their neighbours: an unconditional batch window makes a lone writer — the only writer, when nothing else is queued — wait out the whole window *per commit*, converting a throughput optimisation into a latency floor of the window size. The rule is now "collect while the queue has work; cut at `maxRecords` or `maxDelay`; cut immediately when the queue is empty", and it is asserted as a check ("a lone writer gets no batching at all": 20 sequential appends, 20 forces). The second: the recovery scan hung, because `WalRecovery.readAt` looped on top of `DurableChannel.readAt`, which already loops, so a read at EOF returned `0` — an answer, not a request to retry — and spun forever; found by the contract's exhaustive truncate-offset check, which a "write some records, crash, check" smoke test would never have produced.

**The kill -9 micro-harness** (`dev.ledgerx.wal.crash.CrashHarness`, `./build.sh crash`, its own CI step): fork a child JVM running a `DurableLedger` on a random workload, print one flushed line per ack with its LSN, its end offset and the watermark its force covered, `SIGKILL` it at a random instant, then check the log against what was acknowledged. **Two crash models, because `kill -9` alone cannot test fsync**: a process crash leaves the page cache behind, so all three policies pass that model, and a harness that stopped there would have reported `NO_FSYNC` as clean. The second model also does what the kernel will not — truncate to a random offset at or past the child's last force watermark, discarding exactly the tail no promise covers — which is power loss without a power supply, and its limits are stated: it loses a suffix and nothing else, so it cannot produce a reordering or a controller that lied about a force it accepted.

`./build.sh` also runs a **19-check contract** for the parts a random kill cannot be relied on to hit: exact frame and header bytes; **68 single-bit flips** across length, LSN, type and payload, each truncating at exactly its own record; **all 113 truncate offsets** of a four-record log; head damage refused with the file untouched; unknown type (0x7F *and* 0x00) refused with the file untouched; an LSN hole truncated with the next append taking the cut's number, not the stale one's; per-commit forcing once per record against group commit's 5 forces for 256 frames; the ack watermark never behind an acked record; 206 events replayed identically twice with 206 payloads re-encoding byte-identically; the codec injective over 400 random events plus a 5,900-entry posting; a refused transaction leaving the log byte-identical; a structurally-valid frame the ledger refuses being fatal rather than truncatable; the payload ceiling enforced before the queue.

**The campaign:** 1,000 cycles, 24 ops per child, all five menu entries × both crash models, 6,543 acks observed in 154 s, `killed=100/100` in every row. **Zero invariant violations and zero acknowledged-but-lost transactions under either forcing policy in both models**; `NO_FSYNC` lost **284** acknowledged records across its 100 power-loss cycles, with 98 of those cycles tearing the tail and 3,213 bytes cut. Every one of the 1,000 cycles ended in a real `SIGKILL`. Children run with `-Djdk.tracePinnedThreads=full` and the parent fails a cycle that prints a pinned thread, so ADR 0001's rule is enforced here rather than trusted.

**Stated plainly, what this does not prove.** No power-loss test on real hardware, no lying-controller model, no `O_DIRECT` (its javadoc says it throws where the OS or filesystem declines, so it stays an experiment for the benchmark ticket), no `mmap` write path — ADR 0001's named option is deferred, not rejected, and the lemma above needs re-proving there because `msync` and dirty-page writeback are not offset-ordered; the record format is deliberately offset-addressable so that trial needs no format change. Rotation and retention are unstarted on purpose. And single-node durability is not replication safety.

**Handed to other tickets, as rules rather than notes.** To *How is state proven identical after a crash?*: a snapshot may be written only **after** the WAL bytes it covers are forced, and recovery must refuse a snapshot whose claimed WAL offset the file does not have — the stale-snapshot-with-torn-WAL case is data loss, not a torn tail; fsync the snapshot, then the directory, then truncate or rotate, never the reverse. To *What are ledger-x's idempotency semantics?*: the key and its status get a record type written **in the same group** as the posting, because the log has no cross-record atomicity and a key stored after the ack is a key that can be lost while the money is not — that is the double-payout. To *How do a payout and a refund to the same account never interleave?*: validate → append → ack → apply is one critical section and the ack order must equal the apply order; also, this ticket needed `validate` without `apply` exposed from the domain, did not take it, and `DurableLedger` poisons itself on a storage failure instead — that is now your problem, with the reasoning. To *What must TLC prove?*: `acked ⇒ ∃ force covering these bytes` is the predicate, and the lemma above is small enough to exhaust. To *What breaks it?*: the fault surface is now nameable — kill at an instant, truncate to a byte, scribble inside a payload (must truncate), scribble inside the header (must refuse).

**Fog graduated:** nothing new is *unblocked* by this ticket; the replay state-hash scheme, the chaos fault set's payout half, the benchmark's concurrency shape and the public API surface are all still where they were, and this ADR hands two of them rules rather than questions (details in §10–§11 of the file).
